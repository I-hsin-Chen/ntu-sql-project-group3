# Parser Module Overview

The `parser` package contains the SQL parsing and query plan transformation utilities that sit on top of the DeepDB-inspired learning components in this repository. While other folders focus on training ensembles, evaluating learned cardinality estimators, and compiling probabilistic models, the parser subsystem is responsible for:

- Understanding incoming SQL queries, decomposing them into logical components, and normalizing their syntax.
- Exploring alternative join orders (left-deep, bushy, and exhaustive) using the learned cardinality estimates exposed by `cardinality.py`.
- Executing and benchmarking rewritten queries against a local SQLite copy of the IMDb benchmark so that different plan shapes can be compared empirically.
- Visualizing relational algebra trees that correspond to SQL statements, which helps explain the structure of generated join plans.

The following files implement these responsibilities:

- `my_parser.py` – Wrapper utilities around `sqlparse` that extract base SELECT clauses, projections, identifiers, and WHERE predicates, and that can reorder filters for experimentation.【F:parser/my_parser.py†L1-L88】 These helpers supply the structural information used throughout the rest of the module.
- `utils.py` – Shared helpers for estimating cardinalities through DeepDB's ensembles, normalizing SQL into `CROSS JOIN` form, flattening nested subqueries, and extracting table/condition metadata needed by join enumeration algorithms.【F:parser/utils.py†L1-L116】 The `cardinality_estimation` function bridges the parser to the DeepDB models stored in `imdb-benchmark` by calling `get_cardinality` from the project root's `cardinality.py` module.【F:parser/utils.py†L1-L19】【F:cardinality.py†L1-L20】
- `bushy_tree.py` – Implements a greedy bushy-join enumerator that repeatedly picks the next pair of tables (or subplans) with the minimum estimated join cardinality, materializing subqueries and updating predicates as it merges nodes.【F:parser/bushy_tree.py†L1-L91】 When the recursion collapses to two remaining subplans it emits a fully cross-joined SELECT statement for downstream execution.【F:parser/bushy_tree.py†L92-L118】
- `left_deep.py` – Builds left-deep join trees by seeding the plan with the pair of tables that yields the smallest estimated join cardinality and then iteratively adding the next best table to the growing left spine.【F:parser/left_deep.py†L1-L75】 The resulting SQL is normalized to `CROSS JOIN` form so runtimes can be compared directly in `run_with_sqlite.py`.【F:parser/left_deep.py†L12-L18】【F:parser/left_deep.py†L43-L64】
- `brutal_force.py` – Generates every possible binary join ordering by recursively expanding all table pairings, producing a list of candidate SQL statements in `CROSS JOIN` form.【F:parser/brutal_force.py†L1-L74】 This exhaustive search is used as a baseline when comparing the heuristic join planners.【F:parser/run_with_sqlite.py†L63-L100】
- `run_with_sqlite.py` – Evaluation harness that executes the original and rewritten queries against a local SQLite database populated with the IMDb benchmark, applies timeouts, and records runtimes to `output.csv` for later analysis.【F:parser/run_with_sqlite.py†L1-L101】 It coordinates the bushy, left-deep, and brute-force planners defined above.【F:parser/run_with_sqlite.py†L52-L100】
- `visualize.py` – Constructs relational algebra trees from SQL statements using `sqlparse`, the parser utilities, and Graphviz, producing interactive diagrams that reveal how filters and joins are arranged in generated plans.【F:parser/visualize.py†L1-L129】 The tree construction routines reuse `my_parser.py` helpers and recursively inline subqueries discovered in aliases.【F:parser/visualize.py†L5-L105】

## Relationship to the Rest of the Repository

Most directories in this DeepDB fork (e.g., `ensemble_creation`, `ensemble_compilation`, `rspn`, `aqp_spn`) implement probabilistic models and training pipelines for learned cardinality estimation and approximate query processing. The parser subsystem interfaces with these learned components exclusively through `cardinality.py`, which exposes `get_cardinality` by wrapping DeepDB's sum-product networks.【F:cardinality.py†L1-L20】 As a result, the parser does not contain model training code itself; instead, it consumes trained ensembles to steer join-order search and validate the effectiveness of learned cardinality predictions against a SQL engine. The empirical runtime data produced by `run_with_sqlite.py` can then be analyzed alongside DeepDB's evaluation scripts in the `evaluation` folder, closing the loop between learned models and query-optimization behavior.

Because the parser focuses on SQL rewriting rather than model learning, it remains loosely coupled to the rest of the repository: only the cardinality estimator and the external IMDb benchmark files are required at runtime. This separation allows you to iterate on join enumeration and visualization logic without retraining models, while still leveraging DeepDB's learned components to guide optimization decisions.
